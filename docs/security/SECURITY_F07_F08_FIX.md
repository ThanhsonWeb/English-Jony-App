# StudyJony security remediation — F07 + F08

Date: 2026-10-06. Scope: Topic PATCH ownership and vocabulary creation only. No production accounts/services/data, dependency changes or automatic migrations.

## 1. Confirmed causes

**F07:** `updateTopic` scoped its query to the authenticated owner but passed the entire request body into `findOneAndUpdate`. The body could change the matched topic's owner or creation time and submit internal fields/update operators without an allowlist. Missing owner-scoped topics also returned success with a null result. Deletion was owner-scoped, but returned success for a foreign/missing topic and could clean up the caller's legacy foreign-topic word links before checking whether the topic existed for that owner.

**F08:** `createNewVocab` spread the request body into `Vocab.create`. Overriding `user` prevented owner impersonation, but did not validate optional topic ownership or exclude scheduler/history, timestamps, IDs and source metadata. Model defaults apply only when callers do not override them.

The models, existing vocabulary PATCH allowlist, optional-topic behavior, shared review service, and all current creation callers were inspected before changes.

## 2. Exact allowlists and implementation

| Path | Accepted client fields | Server behavior |
| --- | --- | --- |
| Topic PATCH | `name`, `description` | Copies only own properties into `$set`; retains `{ _id: req.params.id, user: req.user.id }`, validators and the existing `updatedTopic` response. |
| Vocabulary POST | `english`, `vietnamese`, `pronunciation`, `example`, `topic` | Copies only own properties; validates a supplied topic before insertion; sets `user` from the authenticated session. |
| Vocabulary PATCH, preserved | `english`, `vietnamese`, `pronunciation`, `example`, `status`, `topic` | Existing allowlist and owner-scoped query remain. The existing topic validation is shared locally with creation. |

Non-allowlisted fields are **ignored**, allowing existing clients to submit extra metadata without breaking legitimate text saves. `_id`, `user`, `__v`, timestamps, dotted paths, update operators and unrelated internal fields cannot be supplied through the fixed paths.

### Topic ownership and deletion

- Own-topic rename/description edits work normally.
- A request cannot transfer ownership, even alongside a valid rename.
- An owner-scoped missing/foreign PATCH returns controlled **404 `Topic not found`**.
- DELETE checks owner-scoped existence before vocabulary cleanup and keeps the owner predicate on the final deletion. Missing/foreign topics return the same controlled 404.
- Successful own-topic deletion retains its existing **204** response and removes only the authenticated owner's attached words. Other accounts' words and global words are untouched.
- Topic creation was not broadened into this batch.

### Optional topic validation

The local `isOwnedTopic` helper reuses the existing `mongoose.isObjectIdOrHexString` and `Topic.exists({ _id: topic, user: userId })` checks.

- Omitted topic or explicit `null`: valid global notebook creation; no topic is created automatically.
- Existing topic owned by the authenticated user: accepted.
- Foreign, nonexistent, malformed, array or operator-object topic: controlled **400 `Topic must belong to the authenticated user`**, before any word is inserted.
- PATCH topic assignment/clearing preserves its existing behavior. Ordinary PATCH text edits do not revalidate historical topic links that were not changed.

### Server-controlled creation defaults

Existing model defaults/hooks now initialize new words without caller overrides:

- `reviewCount: 0`, `learningLevel: 0`, `status: false`.
- `lastReviewedAt: null`, marking a genuinely never-reviewed word.
- `nextReview` and `createdAt`: server time.
- `_id`: generated by Mongoose; `__v: 0`.
- `source`: absent.

Required text validation, trimming and optional pronunciation/example handling remain unchanged. New words do not earn XP simply by being created. Flashcard/Quiz/Write still use the existing shared review service and its one-hour retry/Due history and reward deduplication.

### Dialogue provenance decision

The current `DialogueUsefulWords` browser component sends `source` to the ordinary vocabulary POST. There is **no trusted server-generated vocabulary provenance path** in this checkout; the task-ID catalogue does not verify word membership or titles. No runtime UI/API reward consumer of vocabulary `source` was found.

Consequently, this batch does not pretend browser-supplied source is authoritative, derive provenance from insufficient task IDs, or introduce a new import endpoint. Vocabulary POST ignores `source`, including real lesson IDs with caller-supplied titles. Dialogue saving still accepts the existing word/meaning/pronunciation/example payload, preserves its saved-state/duplicate checks and writes global notebook words. No dialogue content, UI, progress or XP code was changed.

Any future trusted provenance import needs to derive metadata and word membership from server-controlled content. Existing stored provenance is not retroactively validated by this change.

## 5. Compatibility and existing data

- No migration is required to run the fixed endpoints. Existing accounts, topic/word IDs, learning history, auth cookies, API success shapes and valid optional-topic requests remain compatible.
- Clients that deliberately submit scheduler/source/internal fields at creation now receive server defaults rather than their overrides. This is the intended security change.
- Foreign/missing Topic PATCH/DELETE now return 404 instead of misleading success. Legitimate rename and deletion keep their existing success contracts.
- Existing UI duplicate/pending handling remains; no new word uniqueness rule, automatic topic creation, deduplication migration or learning-data rewrite was added.
- Existing malformed records **may need a separately approved reconciliation**, but production data was not inspected and no prevalence is claimed:
  1. Compare vocabulary owners with referenced topic owners; flag foreign/missing links. For confirmed foreign links, consider clearing the topic to the global notebook while preserving the word's owner/content/history.
  2. A previously transferred topic's original owner cannot reliably be recovered from its current document alone. Establish ownership from trustworthy history/backups/user confirmation before any repair; do not automatically transfer or delete it.
  3. Review suspected forged scheduling/timestamps/provenance against available trusted history. Do not blanket-reset genuine review progress or assume existing `source` is verified.
- No reconciliation/migration was executed or added as an automatic startup operation.
