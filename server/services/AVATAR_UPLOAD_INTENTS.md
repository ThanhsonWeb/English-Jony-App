# Avatar upload intents

The avatar endpoint registers and claims an intent before writing to storage. The separately invoked cleanup worker deletes eligible tracked files; it is not started automatically.

An upload caller supplies a stable, server-generated UUID as `operationId`. Reservation checks and updates the active-account fence in the same transaction as the new record. Reusing that ID for the same owner and input returns the same record; changing its provider or content type is rejected. The storage key is generated by the service, unique, and never reused. The record is retained separately from the user so cleanup can continue after account removal.

`beginAvatarUpload` fences the account, claims a reserved intent, and prequeues cleanup in the same transaction. Only a caller receiving `claimed: true` may start storage. Queueing cleanup prevents a still-reserved intent from being claimed. An upload already claimed may finish after deletion starts, so it remains tracked until it has definitely stopped. A Cloudinary timeout or unverified response is `uncertain`, not `finished`.

Cleanup moves from `none` to `pending`, then one worker may atomically claim an unattached intent whose upload is unstarted or has a definitive success or failure outcome. A claim changes the status to `claimed` and returns a unique token only to the winner. No external cleanup may begin until the claim transaction commits. The claim blocks an unstarted upload, and an uploading, uncertain, or attached avatar cannot be claimed. Older `finished` records without a definitive outcome remain ineligible until reconciled.

Only the claim holder can record success or failure using both the token and cleanup generation. A failure changes the state to `retry`; requeueing creates a new generation and stale results are rejected. A success changes the state to `complete`. A timeout or lost upload response remains `uncertain` until there is definitive evidence that no upload can still arrive. Claims do not expire automatically: even if a worker crashes or loses a claim response, it may have an external request in flight. Recovery needs an explicit procedure that proves the old action cannot continue; a lease timeout alone is not proof.

The endpoint attaches a verified upload under the account fence and updates the user, new intent, and previous managed intent in one transaction. The attached intent cannot be queued for cleanup; a replaced managed avatar is queued. A legacy avatar without an intent is left untouched. Each new storage key is unique, and Cloudinary uploads do not overwrite another asset.

Run `node scripts/run-avatar-cleanup.js` from `server` with the intended DATABASE and Cloudinary configuration to process at most 100 eligible Cloudinary records. Local records are excluded unless `--local-upload-host` is supplied; use it only on the host with the same local avatar directory used for uploads. A missing local file and Cloudinary's `not found` are successful idempotent outcomes. Explicit authentication/rate-limit rejections and local errors are retryable; network failures and unverified provider responses retain the claim. Monitor `held` and `retry` counts and avoid tight retry loops.

Claims never expire. To recover a claimed record after a crash or ambiguous provider response, first stop and fence all worker instances, verify that the original worker cannot resume, and establish from the provider and infrastructure that its request cannot still execute. Elapsed time or a client timeout alone is not proof. If that cannot be established, leave the claim held. With exclusive operator control, use `node scripts/run-avatar-cleanup.js recover <userId> <intentId> --workers-fenced-and-requests-settled`; the same claim is resumed. Do not run multiple recovery commands or start other workers during recovery. The command does not verify the operator's assertion.

`initiateAccountDeletion(userId)` is an internal service. It transitions an active or legacy-active account to `deleting` and, in the same transaction, detaches its currently attached, definitively successful managed intent and queues it for cleanup. Concurrent retries return `initiated: false` after the first commit. If a referenced intent is missing, belongs to another user, or is in an inconsistent state, initiation rolls back instead of guessing a deletion target. A legacy avatar without an intent is retained unchanged and is not queued. The service does not delete the user or call storage providers.

Outstanding uploads must still finish or be reconciled. An upload already in progress stays tracked; after initiation it cannot attach, and its pending cleanup is not claimable until its outcome is definitive. A reserved, unstarted upload cannot begin after initiation. Legacy fixed Cloudinary IDs, historical local files, CDN caches, backups, and older in-flight application versions remain outside this phase. The collection and unique indexes must exist before integration is enabled; pre-existing draft intent records require migration for the new attachment and outcome fields. No public deletion endpoint or permanent account deletion is implemented.

`checkAccountDeletionReadiness(userId)` is an internal, read-only snapshot check. It reports readiness only after initiation, when no legacy avatar is unresolved, every tracked intent has consistent ownership/storage/attachment state, all uploads have definitive outcomes, and cleanup is complete. Pending/retry cleanup, a held claim, unfinished or uncertain upload, missing/mismatched tracking, and unresolved legacy avatars are blockers. Claims do not expire; the checker never releases claims or contacts a storage provider. It does not delete user or intent data and is not exposed as an endpoint.
