# Avatar upload intents

The avatar endpoint registers and claims an intent before writing to storage. There is no cleanup worker yet; pending cleanup records do not delete stored files.

An upload caller supplies a stable, server-generated UUID as `operationId`. Reservation checks and updates the active-account fence in the same transaction as the new record. Reusing that ID for the same owner and input returns the same record; changing its provider or content type is rejected. The storage key is generated by the service, unique, and never reused. The record is retained separately from the user so cleanup can continue after account removal.

`beginAvatarUpload` fences the account, claims a reserved intent, and prequeues cleanup in the same transaction. Only a caller receiving `claimed: true` may start storage. Queueing cleanup prevents a still-reserved intent from being claimed. An upload already claimed may finish after deletion starts, so it remains tracked until it has definitely stopped. A Cloudinary timeout or unverified response is `uncertain`, not `finished`.

Cleanup moves from `none` to `pending`, then to `retry` on failure or `complete` on success. Requeueing a failure creates a new generation. Record results with that generation so delayed results cannot complete or fail a newer retry. Completion is rejected while an upload is `uploading` or `uncertain`; callers may mark `finished` only with definitive evidence that no upload can still arrive. A reserved intent queued for cleanup cannot start and may be completed without an upload.

The endpoint attaches a verified upload under the account fence and updates the user, new intent, and previous managed intent in one transaction. The attached intent cannot be queued for cleanup; a replaced managed avatar is queued. A legacy avatar without an intent is left untouched. Each new storage key is unique, and Cloudinary uploads do not overwrite another asset.

Future account deletion must atomically detach and queue the currently attached asset, and wait for or reconcile outstanding uploads. Before deleting, a worker needs an atomic cleanup claim that prevents subsequent attachment; a state recheck alone cannot close that race. The worker must handle uncertain results conservatively and retry failures. Legacy fixed Cloudinary IDs, historical local files, CDN caches, backups, worker crashes, and older in-flight application versions remain outside this phase. The collection and unique indexes must exist before integration is enabled; pre-existing draft intent records require migration for the new attachment and outcome fields.
