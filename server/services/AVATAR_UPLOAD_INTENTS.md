# Avatar upload intents

This internal tracking layer is not connected to avatar uploads or a cleanup worker yet. It makes no storage calls and does not delete user data.

An upload caller supplies a stable, server-generated UUID as `operationId`. Reservation checks and updates the active-account fence in the same transaction as the new record. Reusing that ID for the same owner and input returns the same record; changing its provider or content type is rejected. The storage key is generated by the service, unique, and never reused. The record is retained separately from the user so cleanup can continue after account removal.

`beginAvatarUpload` fences the account and atomically claims a reserved intent. Only a caller receiving `claimed: true` may start the corresponding upload. Queueing cleanup prevents a still-reserved intent from being claimed. An upload already claimed may finish after deletion starts, so the upload must be tracked until it has definitely stopped. A timeout or lost response is `uncertain`, not `finished`.

Cleanup moves from `none` to `pending`, then to `retry` on failure or `complete` on success. Requeueing a failure creates a new generation. Record results with that generation so delayed results cannot complete or fail a newer retry. Completion is rejected while an upload is `uploading` or `uncertain`; callers may mark `finished` only with definitive evidence that no upload can still arrive. A reserved intent queued for cleanup cannot start and may be completed without an upload.

Future integration must atomically coordinate avatar attachment and cleanup scheduling, prevent cleanup of the currently attached asset, and reconcile unknown upload outcomes. It must also handle legacy fixed Cloudinary IDs, historical local files, provider failures, CDN caches, backups, and worker crashes. This record alone does not provide those guarantees; its unique indexes and the collection must exist before integration is enabled.
